# 未上市与信息稀缺企业调查

## 目录

1. 核心原则与主体消歧
2. 足迹来源矩阵与反向关系图
3. 产品、经营、研发和人员判断
4. 叙事异常与一手调查升级
5. 完成标准与首轮执行顺序

## 核心原则

信息稀缺企业不等于无法研究，只是不能依赖财报叙事。先确认“它是谁”，再从企业无法避免留下的法律、交易、产品、人员和物理足迹拼图。

不要把“未搜索到”写成“不存在”。最终结果通常是区间、关系图、假设和验证清单，而不是伪精确的收入与份额。

## 1. 主体消歧

先建立 `identity_resolution`，确认：

- 法定名称、历史名称、品牌、英文名和常见误写；
- 统一社会信用代码/注册号、域名、ICP备案、地址、电话和邮箱域；
- 商标、专利申请人、认证持有人、产品型号和软件著作权人；
- 子公司、关联方、经销主体、生产主体和收款主体是否为同一控制体系；
- 同名企业、共享地址、共享电话或借壳品牌造成的歧义。

主体未解决时停止写经营结论。地址、电话、域名和产品型号至少两项交叉一致，才可合并实体。

## 2. 足迹来源矩阵

按企业类型选择，不要求每项都有：

将结果写入 `footprint_coverage[]`。即使某维度没有信息，也必须写 `gap`、原因和下一动作，不能从报告中消失。

| 足迹 | 可回答的问题 | 主要陷阱 |
|---|---|---|
| 工商变更、股权、质押、动产抵押 | 所有权、融资压力、关联方 | 注册资本不等于真实资金 |
| 招投标、中标、客户验收 | 客户、价格、交付和复购 | 中标不等于确认收入 |
| 专利、商标、软著、论文、开源 | 技术方向、团队延续、产品路线 | 数量不等于质量和商业化 |
| 认证、型式试验、许可、召回 | 产品存在、量产准备、合规边界 | 取得认证不等于有销量 |
| 环评、能评、排污、土地、消防 | 工厂、产能、设备和扩建节奏 | 批复产能不等于实际利用率 |
| 招聘、社保人数、员工流动 | 组织规模、职能结构和项目优先级 | 招聘意图不等于净增员 |
| 电商、经销商、报价、二手残值 | 产品价格、渠道、库存与生命周期 | 标价不等于成交价 |
| App、网站、开发者、社区 | 活跃、发布节奏和产品问题 | 流量不等于付费用户 |
| 法院、执行、处罚、投诉 | 回款、质量、劳动和合规风险 | 单一案件不能外推总体 |
| 客户/供应商公开材料 | 供应关系、订单和依赖 | 客户 Logo 可能只是试点 |
| 地图、园区、公开照片 | 办公/工厂是否真实存在 | 门牌存在不等于持续经营 |

## 3. 反向关系图

企业自己没有信息时，从外部节点反查：

1. 用产品型号、认证号、专利申请人、域名和地址找到真实主体。
2. 用客户的招标、中标、验收、供应商名录和案例页反查销售。
3. 用供应商年报、认证、设备采购、应收账款和项目公告反查采购与产能。
4. 用投资人组合、创始人历史任职、共同股东和共享联系方式发现关联方。
5. 将关系写入 `relationship_edges[]`，区分 `verified / inferred / alleged`，保留生效时间。

两个网页重复同一公关稿只算一个关系证据。仅因同地址或同电话不能直接认定控制关系。

## 4. 产品与真实需求

- 收集说明书、型号、认证、固件、App 版本、报价、经销商库存、维修件和售后政策。
- 用客户采购理由、部署周期、复购、扩容、取消和迁移判断真实需求。
- 对实体产品追踪材料、核心部件、代工/自制、良率、质保和生命周期。
- 对软件追踪版本节奏、权限、集成、活跃、续费线索和客户切换成本。
- 对用户评论按型号、版本、时间和使用周期聚类；保留正反样本。

“有产品”与“有稳定商业需求”是两条不同结论。

## 5. 规模与经营反推

只有代理变量时填写 `proxy_estimates[]`，始终输出区间：

- B2B：可验证客户数 × 年均合同区间 × 交付概率；
- 制造：设备/产线理论产能 × 利用率区间 × ASP；
- 零售：有效网点 × 单店销量区间 × ASP；
- SaaS：活跃席位/客户区间 × ARPU × 续费率；
- 服务：可交付人员 × 利用率 × 人均产值区间；
- 人员法：分职能人数 × 同类企业人效区间，只作交叉检查。

每项估算写公式、输入证据、上下界、敏感变量和交叉检查。至少两条独立代理链一致，才可升为中置信度。注册资本、融资额、招聘数和网站流量不能单独推导营收。

## 6. 技术和研发潜力

按转化链判断：

`团队连续性 → 技术资产 → 原型/认证 → 量产/上线 → 客户采用 → 复购/成本优势`

- 专利查看权利要求、引用、同族、法律状态、发明人连续性和是否转让，不只看数量。
- 认证、测试和样机只能证明工程进度；量产、客户采用和复购才接近商业验证。
- 招聘方向、设备采购和认证时间线可以领先财报，但必须给其他解释。
- 技术负责人离职、专利转让、长期无续代、认证后无产品，是潜力折损信号。

## 7. 人员与执行

- 按研发、制造、销售、交付、售后和管理拆分公开岗位与人员信号。
- 观察核心人员履历是否覆盖声称能力、团队是否连续、是否集中依赖创始人。
- 观察岗位长期重复、突然撤销、集体招聘或人员集中流向。
- 只使用公开职业信息和汇总信号，不采集私人联系方式或非公开个人数据。

## 8. 叙事欺骗与异常

重点检查：

- 官网客户 Logo 是否能在客户侧找到采购、验收或部署证据；
- “战略合作、试点、MOU、入围”是否被包装成订单或收入；
- 产品照片、工厂照片、团队照片是否复用或来自第三方；
- 声称成立/研发时间是否早于域名、主体、专利和招聘足迹；
- 声称自产是否只有贸易主体，没有环评、设备、人员和认证足迹；
- 注册地址、电话、邮箱、股东和员工是否与多家关联企业重叠；
- 融资、专利、认证和奖项是否被替代成客户采用和利润；
- 公开价格、经销商折扣、招聘和产能行为是否与管理层叙事相反。

无法证实但影响重大的异常进入 `intelligence_items[]`，并保存原始说法证据。

## 9. 必要时升级为一手调查

公开网络达到边际上限后，给出需用户确认的验证动作：

- 以客户身份询价、索取规格书、交期、合同样本或试用；
- 访谈客户、经销商、供应商和公开可联系的前员工；
- 购买样品、拆机、试用、走售后流程；
- 查看合法公开的工厂、展会、门店或园区信息；
- 使用已授权的工商、招投标、海关或市场数据库。

这些动作可能对外暴露研究意图或产生费用，执行前必须取得用户确认。

## 10. 完成标准

信息稀缺企业默认 `research_status: partial`。只有满足以下条件才可标 `complete`：

- 主体已消歧；
- 产品存在和客户需求各有独立证据；
- 至少一条客户或渠道证据、一条组织/产能证据、一条竞争证据；
- 规模判断有两条独立代理链或明确声明无法估算；
- 最大异常已保留并给出下一验证动作；
- 核心结论没有依赖搜索摘要、单一宣传稿或注册资本。

## 11. 首轮执行顺序

1. 用 `research-intake.md` 补齐决策用途、主体边界和已知线索。
2. 运行 `vertical_plan.py`，形成法定名、历史名、品牌、型号、地址的查询矩阵。
3. 先跑政府采购与政府 PDF 采集器，拿到可重复验证的交易/产能候选。
4. 再用 `browser-vertical-workflow.md` 完成工商、专利/商标、ICP、认证和司法查询。
5. 从客户、供应商、渠道、招聘和产品型号反向补图；不要只围绕企业官网正向搜索。
6. 每个维度写 `covered/partial/gap`；公开网络达到边际上限后，才建议询价、访谈或购买样品，并在执行前取得确认。
